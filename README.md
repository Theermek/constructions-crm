# Мини-CRM «Объекты и задачи»

CRM для строительной компании: постановщик ведёт объекты (стройки) и задачи по ним, исполнитель
берёт задачи в работу и сдаёт на проверку. Цикл статусов и история изменений защищены на уровне
базы данных.

**Приложение:** https://constructions-crm.vercel.app

**Стек:** React 19 + TypeScript + Vite, Mantine, TanStack Query, Supabase (Postgres + Auth + REST).

Сопутствующие документы:
- [`SPEC.md`](./SPEC.md) — контракт логики: матрица переходов, матрица видимости, контракт RPC
- [`DECISIONS.md`](./DECISIONS.md) — решения и допущения там, где ТЗ неоднозначно, и что не вошло
- [`EXPLAIN.md`](./EXPLAIN.md) — объяснение устройства системы без технических терминов

## Как запустить

Нужен **Node 22** (на Node 20 актуальный клиент Supabase не работает). В корне лежит `.nvmrc`:

```bash
nvm use           # возьмёт версию из .nvmrc
npm install
cp .env.example .env.local   # и заполнить значениями своего проекта Supabase
npm run dev
```

### Переменные окружения

`.env.local` (в репозиторий не попадает, см. `.gitignore`):

| Переменная | Что это | Где берётся |
| --- | --- | --- |
| `VITE_SUPABASE_URL` | базовый URL проекта, **без** `/rest/v1` | Supabase → Settings → Data API |
| `VITE_SUPABASE_ANON_KEY` | публичный (`publishable`/`anon`) ключ | Settings → API Keys |
| `SUPABASE_SERVICE_ROLE_KEY` | секретный (`secret`/`service_role`) ключ — **только для локальных скриптов** | Settings → API Keys |
| `SUPABASE_DB_PASSWORD` | пароль базы — нужен CLI для применения миграций | Settings → Database |

Первые две попадают в сборку фронтенда — так и задумано: публичный ключ предназначен для
браузера, а доступ ограничивается политиками в базе, а не секретностью этого ключа. Последние две
используются только локальными скриптами и во фронтенд не попадают никогда.

### Развернуть базу с нуля

```bash
npx supabase login
npx supabase link --project-ref <ваш-ref>
npm run db:push     # применит все миграции из supabase/migrations
npm run seed        # создаст пользователей, объекты и задачи
```

Две настройки проекта Supabase в миграции не выносятся, их нужно выставить в панели
(**Authentication → Sign In / Providers → Email**):

- `Enable Email provider` — **включён** (вход по email и паролю)
- `Allow new users to sign up` — **выключен** (открытая регистрация запрещена, п.3.5 ТЗ)
- `Confirm email` — выключен, иначе созданные скриптом пользователи не смогут войти

### Проверка безопасности

```bash
npm run test:security
```

Скрипт под именем обычного исполнителя обращается к базе напрямую, минуя интерфейс, и пытается
сделать запрещённое: прочитать чужие задачи, изменить статус в обход правил, подделать историю,
повысить себе роль. Все попытки должны быть отклонены базой.

### Деплой на Vercel

Framework определяется автоматически (Vite), команда сборки `npm run build`, каталог `dist`.
Что нужно настроить руками:

1. **Переменные окружения** в Settings → Environment Variables: `VITE_SUPABASE_URL` и
   `VITE_SUPABASE_ANON_KEY`. Без них сборка пройдёт, а приложение упадёт при запуске.
   `SUPABASE_SERVICE_ROLE_KEY` и `SUPABASE_DB_PASSWORD` на Vercel **не добавлять**: они нужны
   только локальным скриптам, а всё, что попадает в сборку фронтенда, видно любому посетителю.
2. **Node 22** в Settings → Build → Node.js Version (в `package.json` указан `engines.node >= 22`).

Перенаправление всех путей на `index.html` уже настроено в `vercel.json` — без него прямой заход
на `/objects/<id>` возвращал бы 404, потому что такой страницы на диске нет.

## Как устроена защита

Два независимых слоя в самой базе:

1. **Права на таблицы и колонки** — какие таблицы и какие именно колонки роль вообще может
   трогать. Колонка `status` не выдана на запись никому: сменить статус прямым запросом
   невозможно физически, независимо от политик. Таблица истории доступна клиенту только на чтение.
   Колонка `role` в профиле не выдана на запись — исполнитель не может повысить себя до
   постановщика.
2. **Политики на строки (RLS)** — какие строки роль видит и может менять. Исполнитель видит
   только задачи, где он назначен, и только объекты, где у него есть задачи.

Единственный способ сменить статус — функция `change_task_status(task_id, to_status, comment)`.
Она проверяет роль, назначение, допустимость перехода по матрице из ТЗ и обязательность
комментария при возврате на доработку, после чего сама пишет строку истории. Матрица переходов
дублируется на фронтенде только для того, чтобы не рисовать кнопки, которые не сработают.

Структура:

```
supabase/migrations/   схема, триггеры, RPC, права и политики — вся защита
scripts/seed.mjs       демо-данные; статусы разгоняются настоящими переходами через RPC
scripts/security-tests.mjs  негативные тесты: попытки обойти правила напрямую
src/lib/               клиент Supabase, типы БД, матрица действий для UI, тексты ошибок
src/pages/             экраны: вход, объекты, карточка объекта, карточка задачи, мои задачи
```
