# Решения и допущения

Пункт 4 сдачи. Здесь всё, что я решил сам там, где ТЗ допускает несколько трактовок, плюс то,
что не вошло в объём.

## 1. Где именно живёт бизнес-логика

Решение: вся логика прав и переходов — в Postgres, фронтенд её только отображает.

Статус задачи нельзя изменить обычным запросом на обновление: колонка `status` не выдана
клиентским ролям ни на вставку, ни на обновление. Единственный путь — функция
`change_task_status()`, которая сама проверяет роль, назначение, допустимость перехода и
обязательность комментария, и сама пишет строку истории. Проверка прав на фронтенде
(`src/lib/transitions.ts`) дублирует эту матрицу **осознанно**: она нужна, чтобы не показывать
кнопки, которые всё равно не сработают. Источник правды — база.

## 2. Спорное место в ТЗ: что видит исполнитель в карточке объекта

П.2.2 требует «в карточке объекта — список его задач», п.3.2 запрещает исполнителю читать чужие
задачи. Трактовки взаимоисключающие.

Решение: приоритет у требования безопасности. Исполнитель видит объект, если на нём есть хотя бы
одна его задача, но в списке задач объекта видит **только свои**. Это обеспечено политикой RLS,
а не фильтром в интерфейсе: прямой запрос `GET /rest/v1/tasks?object_id=eq.<id>` вернёт
исполнителю ровно его строки.

Если бизнесу нужно обратное (прораб видит весь фронт работ по стройке) — это меняется одной
политикой и не затрагивает остальной код. Вопрос стоит задать заказчику.

## 3. Прочие решения по функциональности

| Вопрос, на который ТЗ не отвечает | Решение | Почему |
| --- | --- | --- |
| Можно ли создать задачу без исполнителя? | Да, исполнитель необязателен | На практике задачу часто заводят раньше, чем решают, кто её делает. Взять в работу такую задачу нельзя: отдельная ошибка `P0006` |
| Может ли постановщик переназначить исполнителя? | Да, пока задача не принята | Иначе при болезни или увольнении задачу пришлось бы пересоздавать |
| Любой постановщик принимает любую задачу или только автор? | Любой | ТЗ прямо говорит, что постановщик «видит всё» |
| Статус «Принята» — финальный? | Да, выходов из него нет | В ТЗ переходов из него не описано |
| Можно ли редактировать принятую задачу? | Нет | Принятая работа — закрытый документ |
| Комментарий при отправке на проверку | Необязателен | ТЗ требует комментарий только для возврата на доработку |
| Что видно в истории исполнителю? | История только по его задачам | Следствие решения №2 |
| Удаление объекта с задачами | Удаляется вместе с задачами и их историей, с подтверждением в интерфейсе | ТЗ разрешает постановщику удалять объекты. Для продакшена правильнее архивирование — см. «не успели» |
| Несколько исполнителей на одну задачу | Нет, один | В ТЗ поле «исполнитель» в единственном числе |
| Хранить ли email в таблице профилей | Нет | Иначе любой пользователь мог бы вычитать контакты всех остальных. Для работы интерфейса достаточно ФИО |
| Создание задачи как событие истории | Пишется строкой «— → Новая» | П.2.4 требует хранить каждую смену статуса; появление статуса «Новая» — тоже событие |
| Смена исполнителя в истории | Не пишется | П.2.4 говорит именно о смене статуса. Полный аудит-лог — отдельная задача |

## 4. Решения по безопасности, которых ТЗ не требовало прямо

1. **Роль пользователя нельзя изменить из приложения.** Колонка `role` не выдана на обновление
   никому из клиентских ролей; менять её можно только сервисным ключом. Иначе исполнитель
   повысил бы себя до постановщика одним запросом, и вся остальная защита обнулилась бы.
2. **Роль задаётся в `app_metadata`, а не в `user_metadata`.** Первую может писать только
   сервисный ключ, вторая подконтрольна самому пользователю.
3. **Функции объявлены с `set search_path = ''`** и полностью квалифицированными именами. Без
   этого вызывающий мог бы подменить схему и выполнить свой код с правами владельца функции.
4. **Исполнителю не сообщается о существовании чужой задачи.** Попытка сменить статус чужой
   задачи и попытка сменить статус несуществующей задачи дают одну и ту же ошибку «Задача не
   найдена», чтобы нельзя было перебором выяснить, какие задачи есть в системе.
5. **Блокировка строки (`for update`) при смене статуса** — два одновременных запроса не проведут
   один переход дважды.
6. **Таблица истории доступна клиенту только на чтение.** Прав на вставку, изменение и удаление
   нет ни у одной клиентской роли, и политик на запись тоже нет — то есть запись заблокирована
   дважды, независимо друг от друга. Пишут только триггер и функция смены статуса.
7. **У неаутентифицированного клиента нет доступа ни к одной таблице.**

## 5. Технические решения

- **Vite + React + TypeScript, Mantine** как UI-библиотека: дизайн не оценивается, поэтому взяты
  готовые компоненты без кастомной вёрстки.
- **Node 22** обязателен: актуальный клиент Supabase на Node 20 не работает. В корне `.nvmrc`.
- **Миграции** лежат в `supabase/migrations` и применяются через `supabase db push`; состояние базы
  воспроизводится с нуля одной командой. Ничего не создавалось руками через интерфейс Supabase,
  кроме двух настроек аутентификации, которые в миграции не выносятся (см. README).
- **Открытая регистрация выключена** на уровне проекта, в интерфейсе нет и формы регистрации.
  Пользователи создаются скриптом `npm run seed`.
- **Демо-данные создаются настоящими переходами.** Скрипт сидирования не вписывает статусы в базу
  напрямую: он логинится реальными пользователями и двигает задачи через ту же функцию, что и
  интерфейс. Поэтому история в демо-данных подлинная.
- **Публичный ключ (`publishable`/`anon`) лежит во фронтенде — это нормально,** он для этого и
  предназначен. Защита построена на RLS, а не на его секретности. Сервисный ключ используется
  единственным локальным скриптом, в репозиторий не попадает.

## 6. Чего нет в сдаче

| Не сделано | Почему |
| --- | --- |
| Архивирование вместо удаления | Для продакшена правильнее не удалять историю физически, но ТЗ прямо разрешает удаление, а объём ограничен 2–3 часами |
| Полный аудит-лог (кто менял название, описание, исполнителя) | ТЗ требует историю смен статуса; расширение журнала — отдельная задача |
| Дедлайны, приоритеты, вложения, уведомления, комментарии к задаче вне статусных переходов | Вне объёма ТЗ |
| Автотесты интерфейса | Вместо них сделан скрипт негативных тестов безопасности (`npm run test:security`): он проверяет именно то, что оценивается — что база не пускает в обход интерфейса |
| Пагинация и поиск | На демо-объёме не нужны, но на тысячах задач понадобятся |
| Смена пароля и восстановление доступа | Регистрация и самообслуживание отключены по требованию ТЗ; пароли выдаёт администратор |
