# SPEC — единственный источник правды по логике мини-CRM

Документ фиксирует то, что в ТЗ допускает несколько трактовок. Любой код в проекте обязан
соответствовать этому файлу. Если код и SPEC расходятся — прав SPEC.

## 1. Роли

Роль хранится в `public.profiles.role` (enum `user_role`): `manager` (постановщик) |
`executor` (исполнитель). Роль **не может быть изменена пользователем** — UPDATE на колонке
отозван у роли `authenticated`.

## 2. Статусы задачи

enum `task_status`: `new` | `in_progress` | `in_review` | `accepted` | `rework`

Русские подписи в UI: Новая | В работе | На проверке | Принята | На доработке.

## 3. Матрица переходов (единственная, обязательная)

| Из | В | Кто | Доп. условие |
| --- | --- | --- | --- |
| — | `new` | manager | при создании задачи |
| `new` | `in_progress` | назначенный исполнитель | `assignee_id = auth.uid()` |
| `in_progress` | `in_review` | назначенный исполнитель | — |
| `in_review` | `accepted` | любой manager | — |
| `in_review` | `rework` | любой manager | **комментарий обязателен** (непустой) |
| `rework` | `in_progress` | назначенный исполнитель | — |

Любой другой переход запрещён и на уровне БД, и в UI. `accepted` — терминальный.

## 4. Контракт RPC

```
change_task_status(p_task_id uuid, p_to_status task_status, p_comment text default null) -> void
```

Функция `security definer`, единственный законный способ сменить статус. Внутри проверяет:
роль вызывающего, назначение на задачу, допустимость перехода, непустоту комментария для
`in_review → rework`. Сама пишет строку в `task_history`. Коды ошибок:

| Код (SQLSTATE) | Когда |
| --- | --- |
| `P0002` | задача не найдена или не видна вызывающему |
| `P0003` | переход не разрешён из текущего статуса |
| `P0004` | у вызывающего нет права на этот переход |
| `P0005` | комментарий обязателен и не передан |
| `P0006` | задача не имеет исполнителя (нельзя взять в работу) |

Фронтенд показывает человекочитаемое сообщение, маппинг — в `src/lib/errors.ts`.

Прямой `PATCH /rest/v1/tasks { status }` невозможен: GRANT на колонку `status` не выдан никому,
кроме владельца функции.

## 5. Матрица видимости (RLS)

| Таблица | manager | executor |
| --- | --- | --- |
| `profiles` | SELECT все | SELECT все (нужны ФИО автора/исполнителя). Email в таблице не хранится |
| `objects` | SELECT/INSERT/UPDATE/DELETE все | SELECT только те объекты, где есть **его** задача |
| `tasks` | SELECT/INSERT/DELETE/UPDATE(поля) все | SELECT только `assignee_id = auth.uid()`; UPDATE — нет |
| `task_history` | SELECT по всем задачам | SELECT только по своим задачам. INSERT/UPDATE/DELETE — нет ни у кого |

**Решение по спорному месту ТЗ:** в карточке объекта исполнитель видит только свои задачи
(п.3.2 «не может прочитать чужие задачи» приоритетнее п.2.2). Это обеспечено RLS, а не фильтром
в UI: запрос `GET /rest/v1/tasks?object_id=eq.X` вернёт исполнителю только его строки.

## 6. Поля

- `objects`: `id`, `name` (обязательно), `address` (обязательно), `created_at`, `created_by`
- `tasks`: `id`, `object_id`, `title` (обязательно), `description`, `assignee_id` (**nullable**),
  `status` (default `new`), `author_id`, `created_at`, `updated_at`
- `task_history`: `id`, `task_id`, `changed_by`, `changed_at`, `from_status` (nullable — создание),
  `to_status`, `comment` (nullable)

## 7. Экраны и маршруты

| Маршрут | Экран | Доступ |
| --- | --- | --- |
| `/login` | вход по email+паролю | гость |
| `/objects` | список объектов (+ кнопка «Новый объект» для manager) | оба |
| `/objects/:id` | карточка объекта: название, адрес, список задач со статусами (+ «Новая задача» для manager) | оба |
| `/tasks/:id` | карточка задачи: поля, доступные действия, история | оба |
| `/my-tasks` | «Мои задачи» | executor (manager тоже видит пункт, но у него список обычно пуст) |

Регистрации в UI нет вообще — открытая регистрация выключена на уровне проекта Supabase.

## 8. Доступные действия в UI

Чистая функция `availableActions(task, profile): TaskAction[]` в `src/lib/transitions.ts` —
ровно матрица из §3. UI рисует только то, что она вернула. Это дублирование логики БД
**осознанное**: БД — защита, фронт — удобство. Источник правды — БД.

Для `rework` UI обязан потребовать непустой комментарий до отправки запроса.

## 9. Границы для саб-агентов

- `supabase/migrations/**` и `.env*` правит **только владелец трека БД**. Остальным — read-only.
- Если негативный тест безопасности падает — это баг политики, его правит владелец трека БД.
  **Запрещено** ослаблять политику или подгонять тест под текущее поведение.
- Типы БД берутся из `src/lib/database.types.ts` (генерируются `npm run db:types`), руками
  не пишутся и не правятся.
